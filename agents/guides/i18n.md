# i18n — translations contract (lys-front)

Source: `src/tools/translationTools.ts`, `src/tools/i18nTools.ts`,
`src/providers/LocaleProvider/`.

## createComponentTranslations(componentName, translations)

The ONE way to declare component strings. Contract:

- `componentName` MUST end with its layer suffix (`Element`, `Feature`,
  `Restricted`, `Page`) — the registry path is INFERRED from it:
  `ButtonElement` → `lys.components.elements.buttonElement.*`. A wrong suffix
  breaks i18n silently.
- `translations` = `{key: {en: "…", fr: "…"}}` — every locale of
  `I18nLocaleEnum` is enforced by types.
- Returns `{config, useTranslations}`: register `config` in the app's layer
  registry; consume the hook:

```tsx
const {t, common} = useMyComponentTranslations();
t("myKey");                          // component key (typed, interpolation via {values})
t("key", {fallbackToKey: true});     // graceful fallback
common("sharedKey");                 // app-wide shared table (typed by the app wrapper)
```

## Message resolution

`generateI18nMessage(locales, {lys})` flattens the app descriptor (every
registered `translation` config + service tables) into per-locale tables,
passed to `LocaleProvider` as `messageSources`. **A component whose config is
not registered has no messages** — registry entry is part of the pattern.

## RULES

- **R1 — The suffix is the contract** (see above).
- **R2 — All locales required** — the type system enforces it; don't cast
  around it.
- **R3 — Interpolation values are strings** (`{values: {total: String(n)}}`).
- **R4 — Backend error codes** travel as alert KEYS; the app translates them
  in its alert renderer — never inside the component that raised the error.
- **R5 — React-intl shows the raw key when a translation is missing** — an
  untranslated string in the UI is a bug in the registry or the suffix.
